## Activation Contract

- When protecting an endpoint with a guard
- When implementing an authentication strategy (JWT, Google, Guest)
- When accessing the current user in a controller (`CurrentUser`)
- When applying ownership or role permissions

## Hard Rules

- **Access token**: 15 min — `Authorization: Bearer` — in client memory (not `localStorage`)
- **Refresh token**: 30 days — `httpOnly`, `Secure`, `SameSite=Strict` cookie
- **`deviceId`**: generated by the backend — never trusted from the client
- **Guest→registered**: same `deviceId` — continuous traceability
- No guard → public endpoint. Use the `Public` marker to record it explicitly
- An ownership check that is only a filter goes in the controller with criteria, not in the use case
- Business permission logic does not go in the controller

## Decision Gates

| Access | Guard |
|---|---|
| Registered users only (type: user/staff/admin) | `JwtAuthGuard` |
| Guests only | `GuestAuthGuard` |
| Registered or guest (accepts both tokens) | `AnyAuthGuard` |
| Admin | `JwtAuthGuard` + `RolesGuard`, required role `admin` |
| Public endpoint | `Public` marker |

| Permission type | Where | How |
|---|---|---|
| Endpoint access | Controller | Attach the guard |
| Ownership / filter my resources | Controller | Add `userId` to the criteria |
| Simple role check | Controller | `RolesGuard` + required role `admin` |
| Business logic with permissions | Use case | Receives `UserContext`, decides with domain rules |

## Execution Steps

1. Choose the guard and the permission location with the tables above.
2. See `references/strategies.md` for the shared `UserContext` type, how a controller receives the `CurrentUser`, and the ownership and business permission examples.
3. Review the anti-patterns in `references/strategies.md` before finishing.
